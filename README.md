# WeatherWise

Type in a city and WeatherWise tells you what's worth doing there over the next seven days: skiing, surfing, sightseeing outdoors or sightseeing indoors. The four activities are ranked from best to worst, and each one shows how every single day looks.

## a. Project overview

The app has two screens. On the first you search for a city, and on the second you see the four activities ranked for that city's week. Each activity gets a score out of 100, a bar, and seven small day chips, with the best day highlighted. Tap a card and it opens up to show every day's score, along with the reason when a day is ruled out ("Thunderstorm", "No snow on the ground").

The last three cities you opened are remembered for 24 hours. If the network is down when you open one of them again, you still see the forecast, with a small orange line telling you when it was last updated.

All the logic (talking to the APIs, scoring, ranking and caching) is written once in Kotlin and shared between Android and iOS. The screens are native on each platform: Jetpack Compose on Android, SwiftUI on iOS. Android is the full app. The iOS app is deliberately smaller (search, then the ranked list) and exists to show the shared code working on both platforms.

## b. Platform and tooling

## c. Architecture and technical decisions

The architecture is MVVM with only the layers this app needs. The shared module has a handful of files, each with one job: `OpenMeteoClient` talks to the APIs, `RecentCitiesStore` remembers the last three cities, `WeatherRepository` decides between network and saved data, and `ActivityScoring` ranks the activities. Screens talk to the repository through their ViewModel. I left out use-case classes and interfaces with a single implementation, because here they would only pass calls along.

A few decisions shape the code more than anything else:

- **Errors are handled in one place.** Every network call goes through a single function that turns any failure into a small, typed `AppError`: no network, timeout, server error, bad data or unknown. Nothing above the data layer ever throws. The one thing it deliberately doesn't swallow is coroutine cancellation, so leaving a screen really does stop the work.
- **Every screen has one explicit state.** Each screen's state is a sealed type, for example loading, results, no match or failed, rather than a handful of booleans that can contradict each other.
- **ViewModels own the timing.** The search waits until you stop typing (350 ms), and a new search cancels the one still in flight. It's a plain job that is cancelled and restarted, so it reads top to bottom.
- **Native UI instead of shared UI.** I considered Compose Multiplatform. I chose a shared core with native UI because the brief asks for a native app, and native screens are what iOS and Android users expect.
- **iOS talks to Kotlin through one small facade.** That facade returns simple classes, which bridge cleanly into Swift.

## d. How to build and run

**Android**

1. Open the project root in Android Studio. You'll need JDK 21 and Android SDK Platform 37.
2. Run the `androidApp` configuration. From the command line, `./gradlew :androidApp:installDebug` does the same.

**iOS** (macOS with Xcode 16)

```
brew install xcodegen
cd iosApp && xcodegen
open iosApp.xcodeproj
```

Then run the `iosApp` scheme. A build step compiles the shared Kotlin framework automatically.

## e. Tests and testing strategy

```
./gradlew :shared:testAndroidHostTest          # shared logic on the JVM
./gradlew :shared:iosSimulatorArm64Test        # the same tests on the iOS simulator (macOS)
./gradlew :androidApp:testDebugUnitTest        # Android ViewModels + snapshot tests
```

I focused the tests on the parts that can actually be wrong: the scoring rules, the ranking, turning the API's responses into our models, turning failures into the right error, the cache rules, and how the screens behave while you type, retry or go offline. There are 30 tests in all, plus 3 screenshot tests.

I didn't re-test things Android already guarantees, like a ViewModel surviving a rotation. There are no mocks: the tests use the real repository talking to a pretend server (Ktor's MockEngine) and an in-memory DataStore, so they check the code that actually ships, and the shared ones run on iOS too.

For a few of the most important tests, I deliberately broke the code to make sure the test would catch it. Examples: letting a cancelled search turn into an error, and working out "today" in UTC instead of the city's own timezone. Each test failed as it should, and then I restored the code.

## f. API usage notes

The app uses three free Open-Meteo APIs. None of them needs a key.

- **Geocoding** (`geocoding-api.open-meteo.com`) finds cities by name. When nothing matches, the API simply leaves the results out, and the app treats that as "no match" rather than an error.
- **Forecast** (`api.open-meteo.com`) gives seven days of weather. I ask for each day's weather type, top temperature, rain, snowfall, wind and gusts, plus hourly snow depth (the app keeps each day's highest value). I always ask for metric units and `timezone=auto`, so a "day" means a day in that city, not on your phone.
- **Marine** (`marine-api.open-meteo.com`) gives wave height and wave period. This is a third API on top of the two the brief mentions. Without it, surfing could only be guessed from the wind, and that guess ranked surfing first in London. If the marine call fails, or the city is inland, surfing simply shows "No sea data" and the other three activities still rank.

Weather data comes from [Open-Meteo.com](https://open-meteo.com/) under CC BY 4.0, and the app shows that credit on its first screen.

## g. Activity recommendation logic

This is the heart of the app, so here it is in plain words.

**For every day of the week, and for every activity, the app asks the same four questions in the same order.**

1. **Do I know enough to judge this?** Every activity relies on one or two things it can't do without. Surfing needs wave data, and skiing needs to know about snow. If that information is missing, the answer is "no data". This is different from a bad score: an inland city isn't a terrible place to surf, it's just not somewhere you can surf at all, and the app says so honestly.

2. **Is there a deal-breaker?** Some conditions rule an activity out no matter how nice everything else is. A thunderstorm or gusts over 70 km/h rule out everything outdoors. On top of that:
   - **Skiing** is ruled out by freezing rain, or by no snow on the ground with none falling.
   - **Surfing** is ruled out by waves bigger than 4 metres.
   - **Outdoor sightseeing** is ruled out by heavy snow, freezing rain, 38 °C or more, or −15 °C or less.

   A ruled-out day scores 0, and the card shows the reason.

3. **How close is each condition to ideal?** Each condition the activity cares about gets a mark between 0 and 1. It earns full marks anywhere inside its comfortable range, and the mark slides down evenly as conditions drift away from it, reaching zero at a hard limit.

   For example, outdoor sightseeing is happiest between 15 and 25 °C. At 10 °C it still gets two thirds of the marks, and at 0 °C it gets nothing. Rain works the same way but in one direction only: up to 1 mm is fine, and by 5 mm it gets no marks.

4. **How much does each condition matter?** The marks are weighted and added up into a score out of 100. If one reading is missing for a day, that condition is simply left out and the others share its weight.

Here's what each activity cares about, most important first:

| Activity | What it looks for |
|---|---|
| Skiing | Snow on the ground, at least 30 cm for full marks (40 %) · fresh snowfall, 5 cm or more (20 %) · cold, ideally −8 to 2 °C (20 %) · light wind (20 %) |
| Surfing | Waves of 1 to 2.5 m (50 %) · a long wave period, 10 seconds or more (20 %) · light wind (20 %) · warm air (10 %) |
| Outdoor sightseeing | Staying dry (40 %) · a mild 15 to 25 °C (30 %) · light wind (20 %) · a clear sky (10 %) |
| Indoor sightseeing | Always possible. It starts at 30 on a perfect day outside and climbs to 80 as the weather gets worse. It's the fallback, so a great skiing or surfing day still beats a museum. |

**Then the week is put together:**

- Each activity's weekly score is the average of its daily scores. Ruled-out days count as zero, and "no data" days are left out.
- Scores are rounded once, at the very end, so small rounding errors don't add up.
- Activities are sorted from best to worst. If two land on exactly the same score, they keep a fixed order, so the list never shuffles randomly. An activity with no data for the whole week goes to the bottom.
- The best day is the highest-scoring day. If two days tie, the earlier one wins, since sooner is more useful.

**An example.** Take a London day at 14 °C with 3 mm of rain and a 25 km/h wind:

- **Skiing** is ruled out, because there's no snow.
- **Surfing** has no data, because London is inland.
- **Outdoor sightseeing** gets half marks for staying dry, nearly full marks for temperature and most of the marks for wind. That comes to about 67.
- **Indoor sightseeing** comes in at about 47.

So that day, a walk around town beats a museum.

Adding a new activity means adding it to the list of activities and writing one small scoring function. Nothing else changes.

## h. Assumptions

- "The next 7 days" means the city's own local days.
- Snow depth from the forecast model is a fair stand-in for "is there skiing here". The app doesn't know where actual ski resorts are, or whether their lifts are open.
- Surfing needs real wave data, which is why the Marine API is used, as explained above.
- One ranking for the week, plus a day-by-day breakdown, answers "what should I do this week" better than seven separate rankings would.

## i. Trade-offs and omissions

- **The iOS app is smaller than the Android one on purpose:** no recent cities list and no animated search, though it does show the saved-data line. The shared logic underneath is identical.
- **A little screen logic exists twice.** The search delay, for example, lives in both Kotlin and Swift. That's the price of truly native screens, and I think it's worth paying.
- **No live network monitoring.** The app simply tries the network and falls back to the saved copy if that fails. In airplane mode this happens instantly. On Wi-Fi that's connected but not working, it takes up to 8 seconds.
- **Left out:** "use my location", certificate pinning (Open-Meteo rotates its own certificates), and full UI test coverage.
- **The scoring weights are my judgement**, not data-driven. They're named and in one file, so tuning them after real feedback is a one-line change.

## j. Production-readiness notes

Already in place:

- Central error handling.
- Request timeouts.
- Cancellation that's safe to rely on.
- Release builds with code shrinking.

Before shipping for real, I'd add:

- Crash and performance reporting (Crashlytics or Sentry).
- Basic analytics on searches and selections.
- Release signing and store uploads from CI with Fastlane.
- Login and token refresh (Ktor's Auth plugin) once there's a backend that needs it.
- Certificate pinning against our own backend. I'd pin the intermediate certificate's key, always ship a backup pin, and give the pins an expiry date so an old app can never lock itself out.

## k. Cross-platform delivery notes

Here, Xcode builds the shared Kotlin code as part of the iOS build, which is the simplest setup for a single repository.

In a real company, the iOS app usually lives in its own repository and already uses a dependency manager. iOS has two common ones: **CocoaPods** (the older one) and **Swift Package Manager** (Apple's own, built into Xcode).

To share this Kotlin code with that app, you'd compile it into an **XCFramework**: a ready-built bundle of the code for both real iPhones and the simulator. You'd publish each version of it, for example as a zip on a GitHub release. The iOS app then pulls in "SharedCore 1.2.0" exactly as it would any other library. The tool that does the publishing step is a Gradle plugin called KMMBridge.

If the iOS app already uses CocoaPods, Kotlin's CocoaPods plugin does the same job.

I'd lean towards Swift Package Manager. It's built into Xcode, and CocoaPods is being wound down. Either way, the iOS team never has to open a Gradle file.
